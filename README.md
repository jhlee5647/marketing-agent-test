# 리뷰 질의 에이전트

마케터가 한국어로 질문하면, 적재해 둔 Amazon 리뷰 데이터만 근거로 한국어로 답하는 터미널 에이전트다.

```
> 리뷰가 가장 많은 상품 3개와 각각의 평균 별점은?
> 사람들이 끈적임에 대해 뭐라고 해?
> 그럼 5점 리뷰에서는 뭘 칭찬해?
```

답에는 항상 **근거**가 붙는다. 인용한 리뷰의 ID와 원문 한 조각, 또는 실행한 SQL과 그 결과 수치다. 적재한 데이터로 답할 수 없으면 답할 수 없다고 말한다.

이 문서는 처음 온 사람을 위한 것이다. 먼저 돌려 보고, 그다음 왜 이렇게 생겼는지 읽으면 된다.

## 1. 10분 안에 돌려 보기

### 준비물

- Python 3.12와 [uv](https://docs.astral.sh/uv/)
- OpenAI API 키
- 디스크 여유 몇 GB (적재 규모에 따라)

### 설정

`.env.example`을 복사해 `.env`를 만들고 키를 채운다. `.env`는 git에 올라가지 않는다.

```bash
cp .env.example .env
```

| 키 | 쓰는 곳 | 없으면 |
|---|---|---|
| `OPENAI_API_KEY` | 에이전트·임베딩·심판 | 아무것도 안 됨 |
| `OPENAI_MODEL` | 에이전트가 쓰는 채팅 모델 | 에이전트 실행 실패 |
| `EVAL_JUDGE_MODEL` | 평가의 **심판**(에이전트와 다른 상위 모델) | 평가에서 루브릭 케이스를 채점 못 함 |
| `EVAL_HOST_LABEL` | 평가 결과에 남기는 기계 이름 (예: `r7i.xlarge`) | 결과에 `null`로 기록만 됨. 동작에는 지장 없음 |

### 데이터 적재

**에이전트를 쓰려면 먼저 적재해야 한다.** 적재 데이터는 git에 없다(용량과 리뷰 텍스트 재배포 문제 때문). 적재 명령이 UCSD 서버에서 원본을 스트리밍해 걸러 담는다.

```bash
uv run load                       # 기본값: 얼굴 보습 제품 상위 20개 → 리뷰 약 4,700건
```

> **처음이면 이 값 그대로 돌리길 권한다.** 원본 스트리밍이 약 3.7GB라 규모와 무관하게 3분 남짓 걸리고, 임베딩 비용은 몇 센트다. 규모를 키우는 방법은 아래 4절에 있다.

끝나면 `data/`에 이렇게 생긴 것이 만들어진다.

```
data/reviews.db            SQLite — 상품과 리뷰의 정형 데이터
data/vectors.npz           리뷰 임베딩 (float32 행렬 하나)
data/reviews.metrics.json  이번 적재가 얼마나 걸렸고 무엇을 담았는지
```

### 써 보기

```bash
uv run agent
```

REPL이 뜬다. 위의 예시 질문들을 던져 보면 된다. CLI를 끄면 대화는 사라진다.

### 테스트

```bash
uv run pytest        # 67개, 1초 남짓. 네트워크도 API 키도 필요 없다
```

## 2. 읽는 순서

문서가 여러 개인데, 성격이 다르다. 이 순서로 읽으면 헤매지 않는다.

| 순서 | 문서 | 무엇이 들어 있나 |
|---|---|---|
| 1 | **`CONTEXT.md`** | **용어집.** 상품·리뷰·적재 범위·적재 데이터·평가·케이스·궤적·기준선·회귀가 각각 정확히 무엇을 뜻하는지. **이걸 먼저 읽어야 나머지가 읽힌다.** 구현 이야기는 한 줄도 없다 |
| 2 | **`CLAUDE.md`** | 이 저장소에서 일하는 원칙. 사람에게도 그대로 적용된다 |
| 3 | `docs/architecture.md` | 적재 흐름과 질의 흐름을 그림과 예시로. **주의: 일부가 MVP 시절 서술이다 (아래 참고)** |
| 4 | `docs/adr/` | 되돌리기 어려운 결정 네 개와 그 이유 |
| 5 | `docs/research/amazon-reviews-2023.md` | 원본 데이터셋의 스키마·크기·품질 조사 |
| 6 | `docs/agents/` | 이슈 트래커·라벨·브랜치·도메인 문서 규약 |
| 7 | `evals/reports/` | 실제로 측정한 결과들. 특히 규모 곡선 두 개 |

### `docs/architecture.md`를 읽을 때 주의할 점

MVP(첫 단계) 완성 시점에 쓴 문서라, 저장 형식 설명은 최신으로 갱신됐지만 **다음 두 가지는 지금과 다르다.**

- "적재 기능은 메타에서 **얼굴 보습 제품**을 고른다" → 지금은 적재할 카테고리(**적재 범위**)가 실행 인자다. 얼굴 보습은 기본값일 뿐이다.
- "MVP에 없는 것: … 얼굴 보습 제품 외 카테고리" → 지금은 `--scope`로 넓힐 수 있다.

문서 안의 상품명·수치·리뷰 ID는 문서 스스로 밝히듯 **전부 지어낸 예시**다. 실제 수치는 `evals/reports/`에 있다.

## 3. 시스템이 어떻게 생겼나

흐름이 둘이고, 둘은 **적재 데이터**를 통해서만 만난다.

```
[적재]  UCSD 원본 .jsonl.gz  ──스트리밍──▶  거르기 ──▶  SQLite + 벡터 파일
         (메타 711MB, 리뷰 2.96GB)                        (= 적재 데이터)
                                                              │
[질의]  마케터 ──▶ CLI ──▶ 에이전트(LLM) ──┬── run_sql ───────┤
                                          └── search_reviews ─┘
```

**에이전트는 도구 두 개만 안다.**

| 도구 | 하는 일 |
|---|---|
| `run_sql` | 읽기 전용 SELECT를 실행한다. 최대 50행. SQL 오류는 예외가 아니라 메시지로 에이전트에게 돌아가서, 에이전트가 스스로 고쳐 다시 시도한다 |
| `search_reviews` | 검색어를 임베딩해 리뷰를 의미 검색한다. 상품·별점 범위·구매 인증으로 필터를 건다. 리뷰가 영어라 검색어는 영어로 넘긴다 |

같은 리뷰가 SQLite와 벡터 파일에 **같은 `review_id`** 로 들어 있다. 그래서 검색으로 찾은 리뷰를 SQL로 다시 조회할 수 있고, 반대도 된다.

**저장소는 둘 다 파일 하나다.** 서버도 컨테이너도 없다.

- 정형 데이터는 SQLite (`reviews.db`)
- 리뷰 임베딩은 L2 정규화한 float32 행렬 하나 (`vectors.npz`). 리뷰 **본문은 여기 없다** — SQLite에서 읽는다. 검색은 전수 비교다(근사 검색 아님)

왜 이런 선택인지는 ADR-0001(LangChain/LangGraph), ADR-0004(float32 행렬)에 있다.

## 4. 규모를 바꾸기

적재할 **범위**와 **상품 수**가 둘 다 실행 인자다.

```bash
# 얼굴 보습 제품 상위 100개
uv run load --top-n 100 \
            --db data/scale/face-n100/reviews.db \
            --vectors data/scale/face-n100/vectors.npz

# Skin Care > Face 전체 (리뷰 약 108,000건)
uv run load --scope 'Skin Care > Face' --top-n all \
            --db data/scale/skin-care-face-all/reviews.db \
            --vectors data/scale/skin-care-face-all/vectors.npz
```

- `--scope`는 원본 카테고리 경로에서 루트(`Beauty & Personal Care`)를 뺀 부분을 `>`로 잇는다.
- `--top-n`은 **적재 범위 안에서 2023년 리뷰가 많은 순**으로 고른 상품 수다. `all`이면 전량.
- **기간은 인자가 아니다.** 2023년 리뷰만 담는 것은 상수다.
- 매번 **처음부터 다시 만든다.** 이어 담지 않는다.

규모마다 디렉터리를 따로 주는 것이 관례다: `data/scale/<규모 라벨>/`. 규모 라벨은 적재 인자에서 기계적으로 나오고 적재가 끝날 때 화면에 찍힌다.

원본 데이터가 얼마나 큰지는 이미 재 놨다(2023년 리뷰 기준).

| 적재 범위 | 상품 | 2023년 리뷰 |
|---|---:|---:|
| 얼굴 보습 (`Skin Care > Face > Creams & Moisturizers`) | 5,114 | 36,086 |
| `Skin Care > Face` | 16,940 | 107,969 |
| `Skin Care` | 40,215 | 269,114 |
| 전체 (`Beauty & Personal Care`) | 216,323 | 1,676,896 |

## 5. 데이터에 대해 미리 알아야 할 것

원본은 [Amazon Reviews 2023](https://amazon-reviews-2023.github.io/)(UCSD)이다. 함정이 몇 개 있고, 모르면 틀린 답을 만든다.

- **`rating_number`와 `average_rating`은 원본 메타의 전 기간 값**이다. 적재한 2023년 리뷰 수와 순위가 다르다. "리뷰가 가장 많은 상품"을 물으면 **적재된 리뷰를 직접 세야 한다.** 과거에 실제로 틀린 답이 나왔던 자리다(이슈 #17).
- **`store`와 `details.Brand`는 브랜드가 아닐 수 있다.** 재판매자 이름이 들어간 경우가 많다. 브랜드는 상품명(`title`)으로 판단한다.
- **`price`는 절반 가까이 비어 있다.**
- **카테고리 경로에 오분류가 섞여 있다.** `Skin Care` 아래에 샴푸 1,271개, 다이슨 청소기 필터 114개, 키보드 8개 같은 것이 있다. 적재 범위를 넓히면 그것들이 따라 들어온다. 벡터 개수를 재는 데는 문제가 없지만, **넓은 범위에서 나온 답변을 "스킨케어 전문가의 답"으로 읽으면 안 된다.**
- **2023년 리뷰만 담는다.** 원본은 2023-09에서 끝난다. 2024년 이야기는 데이터에 없다.
- **리뷰 텍스트는 저장소에 커밋하지 않는다.** 데이터셋 라이선스가 명시돼 있지 않아 재배포하지 않기로 했다. `data/`와 `evals/details/`가 `.gitignore`에 있는 이유다.

## 6. 평가 하네스

프롬프트나 저장소를 바꿨을 때 **나빠졌는지**를 사람 눈이 아니라 수치로 판정하는 장치다. 이게 이 저장소에서 가장 특이한 부분이라 조금 자세히 적는다.

```bash
uv run eval                       # 케이스 18개 × 3회. 10~25분, 토큰 약 40만
```

### 무엇을 재나

**케이스** 하나는 질문(또는 이어지는 질문 여러 개)과 기대값이다. 18개가 여섯 유형을 3개씩 덮는다: 집계 · 주제 · 혼합 · 후속 · 거절 · 범위 밖. 전부 `evals/cases.toml`에 사람이 읽을 수 있게 들어 있다.

한 회차가 **통과**하려면 셋을 다 만족해야 한다.

| | 보는 것 |
|---|---|
| **답변 채점** | 집계 질문은 기대 SQL을 평가 시점에 실행해 수치를 대조한다. 정답이 하나가 아닌 질문은 **심판**(다른 상위 모델)이 루브릭으로 채점한다 |
| **궤적 채점** | 도구를 **어떤 순서로 어떤 인자로** 불렀는가. 답이 맞아도 경로가 틀리면 실패다. 예: 상품을 한정한 질문인데 필터 없이 검색했다 |
| **근거 검증** | 인용한 `review_id`가 실제로 있는가. 답변 속 SQL을 다시 돌리면 같은 수치가 나오는가 |

### 어떻게 판정하나

- **회귀는 케이스 단위**다. 기준선에서 `3/3`이던 케이스가 `1/3` 이하로 떨어지면 그 하나만으로 회귀다. **총점은 판정에 쓰지 않는다** — 한 케이스가 무너지고 다른 케이스가 좋아지면 총점은 그대로인데 실제로는 약속이 깨진 것이기 때문이다.
- **소요 시간과 토큰은 기록만 한다.** 합격 판정에 쓰지 않는다. 품질을 올리는 변경이 시간 기준에 걸려 되돌려지는 일을 막기 위해서다.
- **규모가 다르면 품질을 비교하지 않는다.** 데이터가 다르면 정답도 다르다. 하네스가 비교를 거부하고 시간·자원만 견준다.

### 결과가 어디에 남나

| 경로 | 무엇 | git |
|---|---|---|
| `evals/runs/` | 평가 결과 JSON. 다음 평가의 **기준선**이 된다 | 커밋함 |
| `evals/reports/` | 사람이 읽는 마크다운 리포트 | 커밋함 |
| `evals/scale/` | 축약 측정(아래) | 커밋함 |
| `evals/details/` | 답변 전문과 인용된 리뷰 원문 | **커밋 안 함** |

### 축약 측정

규모별 시간·자원 곡선을 그릴 때는 전체 평가가 필요 없다. 규모가 다르면 어차피 품질을 비교하지 않으므로, 중간 규모에서 심판을 부르는 것은 읽지도 않을 값에 돈을 쓰는 일이다.

```bash
uv run eval --case agg-total-reviews --case topic-stickiness --case mix-verified-praise --runs 1
```

`--case`를 주면 케이스 전부를 돈 것이 아니므로 **평가가 아니라 축약 측정**이 되고, 심판 없이 `evals/scale/`에 규모 라벨로 남는다. 기준선 탐색에도 잡히지 않는다. 2분이면 끝난다.

기성 평가 프레임워크를 쓰지 않은 이유는 ADR-0003에 있다.

## 7. 지금까지 한 일과 현재 한계

작업이 세 단계로 진행됐다. 커밋과 이슈를 따라가기 전에 이 지도를 보면 길을 잃지 않는다.

| 단계 | 스펙 | 만든 것 |
|---|---|---|
| 1. MVP | 이슈 #1 | 에이전트 CLI, 두 도구, 적재 |
| 2. 평가 하네스 | 이슈 #9 | 위 6절 전부 |
| 3. 규모 확대와 병목 개선 | 이슈 #23 | 규모를 실행 인자로, 곡선 측정, 저장소 교체 |

세 번째 단계가 이 저장소에서 가장 읽을 거리가 많다. **규모를 로그 스케일로 일곱 단계 키우며 어디가 먼저 무너지는지 재고, 곡선이 가리킨 곳만 고치고, 같은 규모에서 다시 쟀다.**

"무너진다"를 세 층으로 나눠 판정한다.

| 층 | 뜻 | 자 |
|---|---|---|
| **깨짐** | 끝까지 돌지 못한다 (OOM, 디스크 부족) | 이진 |
| **못 씀** | 돌지만 사람이 못 기다린다 | 세션 시작 30초 · 질문당 중앙값 10초 |
| **꺾임** | 규모 대비 자원 증가율이 바뀐다 | 로그-로그 곡선의 기울기 변화 |

> 이 임계값들은 **합격 판정에 쓰지 않는다.** 한계 규모를 말하기 위한 자다.

| 못 씀 (세션 시작 30초) | 리뷰 약 41,000건 *(관측)* | 리뷰 약 630,000건 *(외삽)* |
| 깨짐 (RAM) | 리뷰 약 240,000건 *(관측)* | 리뷰 약 4,000,000건 *(외삽)* |

**바뀐 것은 배수가 아니라 곡선의 모양이다.** 전에는 로드 시간의 60%가 JSON 실수 파싱이라 CPU에 걸린 곡선이었는데, 지금은 파일 크기 ÷ 볼륨 대역폭의 I/O 직선이다. 파싱은 규모와 무관한 약 1초로 내려앉았다. **이제 CPU를 키우는 것은 아무것도 바꾸지 않고, 볼륨을 두 배 빠른 것으로 바꾸면 한계가 두 배가 된다.**

### 솔직한 한계

- **개선 후의 두 벽은 관측이 아니라 외삽이다.** 사다리 가장 큰 점보다 2.4배·15배 밖에 있다.
- **원본의 가장 큰 칸(뷰티 전체, 2023년 리뷰 167.7만 건)은 아직 못 담는다.** 그 규모에서 세션 시작이 약 79초로 30초 벽을 2.6배 넘는다. RAM은 더 이상 문제가 아니다(약 10.6GB).
- **품질 총합은 두 규모에서 모두 조금 내려갔다**(54/54→49/54, 52/54→50/54). 케이스 단위 회귀는 **0건**이고 잡음으로 보이지만, 그것을 "품질이 나빠지지 않았다"로 읽어서는 안 된다. **말할 수 있는 것은 "케이스 단위 회귀는 없다"까지다.** 회차 간 분산을 잰 적이 없어서다(이슈 #41).

자세한 수치는 `evals/reports/scale-curve-float32-matrix-vs-in-memory-vector-store.md`에 있다. 개선 전 곡선은 `scale-curve-in-memory-vector-store.md`다.

## 8. 일하는 방식

- **결정의 원본은 GitHub 이슈**다. `docs/agents/issue-tracker.md` 참고. 스펙 이슈(#1, #9, #23)가 큰 결정을, 하위 티켓이 구현 단위를 담는다.
- **되돌리기 어려운 결정은 ADR**로 남긴다(`docs/adr/`). 세 조건을 다 만족할 때만 쓴다: 되돌리기 어렵고, 맥락 없이는 놀랍고, 진짜 트레이드오프가 있었을 것.
- **용어는 `CONTEXT.md`를 따른다.** 코드·이슈·커밋에서 용어집에 없는 동의어를 쓰지 않는다.
- **브랜치**: 티켓당 브랜치 → PR → merge commit. 계획 문서는 `main`에 직접 커밋한다. 자세한 것은 `docs/agents/branching.md`.
- **문서와 커밋 메시지는 한글로 쓰고, 날짜는 쓰지 않는다.**
- **`CLAUDE.md`의 네 원칙**은 사람에게도 그대로 적용된다. 요약하면: 코딩 전에 생각한다 · 단순함이 먼저다 · 필요한 곳만 고친다 · 검증 가능한 목표를 세운다.

## 9. 처음 부딪히는 것들

- **적재 없이는 아무것도 안 된다.** `data/`가 비어 있으면 `uv run agent`도 `uv run eval`도 실패한다.
- **적재는 규모와 거의 무관하게 3분 이상 걸린다.** 대부분이 원본 3.7GB 스트리밍이라 고정 비용이다. 규모를 키우면 임베딩 시간만 늘어난다.
- **평가는 돈과 시간을 쓴다.** 한 번에 10~25분, 에이전트 토큰 약 40만 + 심판 약 2만. 습관적으로 돌리지 말고, 무엇을 확인하려는지 정하고 돌린다.
- **같은 평가를 두 번 돌리면 통과 수가 다르다.** LLM 출력이 매번 달라서 49/54와 54/54 사이를 오간다. 그래서 케이스마다 3회씩 돌리고 케이스 단위로 판정한다.
- **`load_dotenv()`를 인자 없이 부르면** 파이썬이 표준 입력으로 코드를 받을 때 터진다(`assert frame.f_back is not None`). 스크립트 파일로 두거나 경로를 명시한다.
- **`src/review_agent/eval/cli.py` 맨 아래 `_commit()`은 죽은 코드다.** import되지 않은 `subprocess`를 참조한다. 아무도 부르지 않아 문제를 일으키지 않지만, 보고 놀라지 않도록 적어 둔다.
