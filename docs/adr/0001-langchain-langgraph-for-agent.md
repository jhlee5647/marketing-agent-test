# 도구 2개짜리 에이전트에 LangChain/LangGraph를 쓴다

에이전트는 LangChain v1의 `create_agent`(LangGraph 기반)로 만든다. 세션 안의 대화는 LangGraph `InMemorySaver` 체크포인터로 유지한다. 기술적인 이유로 고른 것이 아니다. 이 프로젝트는 테스트용 개발이고, 목표로 하는 채용 공고가 LangChain/LangGraph를 필수 기술 스택으로 요구하기 때문에 이 스택을 직접 써 보는 것 자체가 목적에 포함된다.

## 왜 의아해 보이는가

이 에이전트가 하는 일은 도구 2개(`run_sql`, `search_reviews`)를 오가는 ReAct 루프 하나다. 이 정도 규모라면 보통은 OpenAI SDK의 도구 호출만으로 루프를 직접 짠다.

- **코드량**: 루프는 "모델 호출 → 도구 실행 → 결과를 메시지에 붙여 다시 호출"의 반복이다. 수십 줄이면 되고, 프레임워크를 써도 줄어드는 코드가 거의 없다.
- **투명성**: 직접 짠 루프는 프롬프트와 메시지가 코드에 그대로 드러난다. 프레임워크를 쓰면 시스템 프롬프트 조립, 도구 스키마 변환, 메시지 상태 관리가 추상화 뒤로 숨는다. 에이전트가 이상하게 굴 때 원인을 찾기가 더 어렵다.
- **의존성**: LangChain은 버전이 올라갈 때 API가 자주 바뀌어 왔다. 도구 2개를 위해 큰 의존성 트리와 그 변화 속도를 떠안게 된다.
- **대화 유지**: 이 에이전트에 필요한 대화 유지는 메시지 리스트를 버리지 않는 것으로 충분하다. 체크포인터와 `thread_id`라는 개념이 따로 필요하지 않다.

## Consequences

- 루프를 직접 제어해야 할 일이 생기면 SDK로 옮기지 말고 LangGraph `StateGraph`로 내려간다. 이 스택을 쓰는 목적이 유지되어야 하기 때문이다.
- 벡터 저장소도 LangChain vectorstore 인터페이스로 다룬다. 그래서 MVP 이후 Chroma를 다른 저장소로 바꿀 때 교체 비용이 작다.
