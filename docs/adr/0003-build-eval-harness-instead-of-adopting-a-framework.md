# 평가 하네스는 기성 프레임워크 대신 직접 만든다

스펙 #9는 케이스를 실행해 답변 품질과 궤적을 채점하고 모듈별 소요 시간과 토큰을 기록하는 평가 하네스를 만든다. 에이전트 평가용 프레임워크가 여럿 있는데도 직접 만들기로 했다. 판단은 이 시스템의 요구 다섯 개를 기준으로 했다: 최종 답변 채점, 궤적 채점, 모듈별 소요 시간, 회귀 비교, 결과가 저장소에 남고 새 계정·새 서버가 필요 없을 것.

결정적인 이유는 둘이다.

**궤적 채점의 의미론이 안 맞는다.** 스펙 #9는 궤적을 "부분 순서 + 금지 패턴"으로 채점한다. 기대한 호출 사이에 다른 호출이 끼는 것은 허용하고(검색어를 바꿔 여러 번 검색하는 것은 의도된 동작이다), 대신 나타나면 안 되는 호출을 케이스마다 적는다. 기성 궤적 평가기가 제공하는 모드는 완전 일치·순서 무관·부분집합·상위집합 네 가지이고, 여기에 금지 패턴을 표현하는 수단을 찾지 못했다. 완전 일치를 쓰면 추가 검색이 회귀로 잡히고, 부분집합을 쓰면 "상품 필터 없이 검색했다" 같은 실패가 통과한다.

**필요한 배관이 이미 의존성 안에 있다.** `langchain_core`의 `RunCollectorCallbackHandler`가 LLM 턴과 도구 호출별 시작·종료 시각을 담은 트리를 모아 준다. 궤적은 결과 메시지의 `tool_calls`에서 읽고, 토큰은 `AIMessage`의 사용량 메타데이터에서 읽는다. 추가 설치가 없다.

여기에 더해, **어떤 프레임워크를 얹어도 사라지지 않는 일이 남는다.** LangChain에는 임베딩 호출용 콜백이 없다. 스펙이 요구하는 "임베딩 API 왕복과 벡터 저장소 로드를 따로 재기"는 어느 쪽을 골라도 직접 계측해야 한다.

## 고려한 대안

- **`agentevals`(LangChain)**: 궤적 평가에 가장 가까운 도구이고 LangSmith 문서가 여기로 보낸다. 하지만 PyPI 배포가 0.0.9에서 멈춰 있고(2025-07-24), LangChain v1 대응 코드는 저장소에만 있다. 설치되는 아티팩트와 저장소의 내용이 다르다. 금지 패턴도 표현하지 못한다.
- **Ragas**: 비정형 데이터 평가 메트릭과 테스트셋 생성기를 함께 제공한다. 그러나 저장소가 약 7개월간 갱신되지 않았고(마지막 push 2026-02-24), 회사가 다른 사업으로 옮겼으며, 유지보수가 끝나 가는 `langchain-community`에 하드 의존해 그것을 우리 lockfile에 끌어들인다.
- **DeepEval**: 에이전트 메트릭이 가장 풍부하고 서버가 필요 없으며 활발히 유지된다. `create_agent`를 문서가 명시한다. 실질적인 2순위다. 채택하지 않은 이유는 위의 궤적 채점 의미론 하나다. 심판을 강화해야 할 상황이 오면 여기부터 다시 본다.
- **MLflow**: `ToolCallCorrectness`·`ToolCallEfficiency`가 있고 실험 이력 UI가 회귀 비교에 가장 잘 맞는다. 다만 결과가 자기 저장소에 살아서, 저장소에 커밋되는 결과 파일을 기준선으로 삼는다는 요구와 어긋난다.
- **LangSmith·Braintrust·Langfuse**: 각각 계정이 필요하거나(자체 호스팅은 Enterprise), 자체 호스팅에 컨테이너 여섯 개가 필요하다. 개발자 한 명의 로컬 작업에 비해 값이 맞지 않는다.
- **OpenAI Evals(호스팅)**: 플랫폼과 API가 2026-11-30에 종료된다.

## 평가 데이터 생성도 직접 한다

케이스 생성기(Ragas의 테스트셋 생성 등)도 쓰지 않는다. 우리 케이스 하나는 질문만이 아니라 기대 궤적, 금지 패턴, 기대 SQL, 규모 자리표시자, 사람이 매긴 라벨로 이뤄진다. 생성기가 덮는 면적은 그중 질문 하나다. 게다가 우리 코퍼스는 문서가 아니라 짧은 리뷰 수천 건이라, 문서 기반 합성은 리뷰 한 건에 대한 단건 질문을 만들기 쉽다. 마케터의 실제 질문은 여러 리뷰에 걸친 집계·요약이라 성격이 다르다.

정형 쪽에서는 통념을 그대로 따른다. 기대값을 값으로 박지 않고 기대 SQL로 적어 평가 실행 시점에 돌리고(실행 정확도와 같은 방식이다), 케이스를 작성할 때 모든 기대 SQL을 실제로 실행해 에러가 없고 결과가 비어 있지 않은 것만 채택한다.

## Consequences

- 새 의존성이 없다. 새 API 키는 심판 모델 이름 하나뿐이고, 새 서버는 없다. 평가 결과가 저장소에 남아 회귀 비교의 기준선이 된다.
- 궤적 채점의 엣지케이스(병렬 도구 호출, 같은 도구의 중복 호출, 인자 부분 일치)를 직접 다뤄야 한다. 기성품이 이미 다룬 문제다.
- 심판의 판정 품질을 빌려 오지 않으므로, 사람이 매긴 라벨과의 일치율로 스스로 검증한다. 일치율이 낮으면 심판만 DeepEval 쪽으로 옮기는 것을 먼저 검토한다 — 하네스 전체를 갈아타지 않는다.
- 케이스를 18개에서 크게 늘리게 되면(예: 100개) 생성기를 쓰지 않는다는 판단은 다시 본다. 손으로 쓰는 비용이 그때는 다른 값이 된다.
- 이 결정은 스펙 #23(규모 확대와 병목 개선)에서 저장소를 바꿀 때 다시 올라온다. 하네스는 에이전트와 계측 래퍼만 주입받아 저장소 종류를 모르므로, 그때 고칠 곳은 케이스 파일의 SQL과 적재 측정을 읽는 부분이다.
