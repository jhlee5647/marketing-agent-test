# 리뷰 벡터는 JSON 대신 float32 행렬 파일로 저장하고, 행렬 하나로 상주시킨다

ADR-0002를 뒤집는다(그 문서의 Status를 `superseded by ADR-0004`로 바꿨다). ADR-0002가 벡터를 들여쓰기된 JSON으로 저장한 것은 Chroma를 쓸 수 없어 `InMemoryVectorStore`를 고른 데 딸려 온 결과였고, 같은 문서가 이미 출구를 적어 두었다: "시간 대부분은 JSON 실수 파싱이라, CLI 시작이 문제가 되면 벡터를 바이너리(numpy 등)로 저장하도록 바꾼다." 스펙 #23의 규모 곡선(#29)이 그 시점이 왔다는 것을 관측으로 보였다.

## 곡선이 잰 것

리뷰 4,744건에서 269,114건까지 일곱 점을 적재해 쟀다(`evals/reports/scale-curve-in-memory-vector-store.md`). r7i.xlarge · RAM 33.1GB · EBS 지속 132MB/s.

**가장 낮은 벽은 세션 시작 30초이고, 리뷰 약 41,000건에서 발화한다.** 보간이 아니라 관측 두 개 사이에 낀 값이다 — 점 3(36,086건 · 콜드 25.6초)은 통과하고 점 4(53,445건 · 39.7초)는 통과하지 못한다. 사다리 안의 다른 벽은 OOM(리뷰 약 240,000건)뿐이고 5.7배 높다. 질문당 중앙값 10초는 일곱 점 어디에서도 도달하지 않았다.

콜드 로드·순수 읽기·파싱·벡터 파일 크기·상주 RAM은 일곱 점 내내 로그-로그 기울기가 1.00 ± 0.05다. **꺾임이 없다는 것은 자연스러운 완충이 없다는 뜻**이고, 읽기와 파싱이 같은 비율로 커지므로 둘 중 하나만 고쳐서는 벽이 2배도 밀리지 않는다.

이 벽의 재료는 **벡터 파일 하나**다. 리뷰당 40.7KB의 JSON 실수 표현이 네 가지 비용을 한꺼번에 만든다.

| 비용 | 곡선이 잰 값 |
|---|---|
| 순수 읽기 | 0.31 ms/건 |
| 파싱 | 0.45 ms/건 |
| 상주 RAM | 104 KB/건 |
| 검색 한 번마다의 일시 행렬 | 36 KB/건 |

**네 번째가 곡선의 새 발견이다.** `InMemoryVectorStore`는 벡터를 파이썬 리스트로 들고 있어서, `similarity_search`를 부를 때마다 필터를 통과한 벡터 전부를 numpy 행렬 하나로 **새로 복사한다.** 상품을 한정한 검색은 남는 것이 적어 비용이 리뷰당 2.1µs로 평평하지만, 한정하지 않은 검색은 점 3의 리뷰당 41.6µs에서 점 5의 110µs로 꺾여 올라간다(로그-로그 기울기 +1.88). 점 5에서는 상주 11.4GB 위에 1.33GB짜리 일시 행렬이 얹혔다.

**점 7을 죽인 것이 이것이다.** 적재(피크 21.29GB)도 세션 시작(28.13GB)도 견뎠는데, 전체 평가가 케이스를 돌기 시작하고 110초 뒤 `269,114 × 1,536` 행렬이 새로 잡히면서 31.04GB에서 커널 OOM 킬러에 SIGKILL로 죽었다.

## 결정

리뷰 벡터 저장소를 `.npz` 파일 하나로 바꾸고, 열 때 **L2 정규화된 float32 행렬 하나**로 상주시킨다. 파일에 담는 것은 검색과 필터에 필요한 것뿐이다.

| 배열 | 담는 것 |
|---|---|
| `vectors` | float32 `(리뷰 수, 1536)`, L2 정규화 |
| `ids` | 행마다의 `review_id` |
| `parent_asins` · `ratings` · `verified` | 필터 세 개 |

1,536차원 float32는 리뷰당 6.1KB다. **6.7배 축소**이고, 읽기·파싱·상주가 같이 줄어든다. 정규화해 두었으므로 검색 한 번은 그 행렬과 질의 벡터의 곱 하나이고, **저장된 것을 다시 복사하지 않는다.** 필터는 파이썬 함수가 아니라 numpy 불리언 마스크로 건다.

**리뷰 제목과 본문은 벡터 파일에 넣지 않는다.** 이미 SQLite `reviews`에 있다. 상위 k건(기본 10건)의 제목·본문만 결과를 만들 때 `review_id`로 읽는다. 리뷰당 104KB 상주의 나머지가 리뷰 텍스트의 파이썬 표현인데, 같은 것을 두 군데 들고 있을 이유가 없다.

**필터 세 열은 SQLite가 아니라 벡터 파일에 둔다.** 리뷰당 15바이트라 가장 큰 점에서도 4MB다. SQLite에서 읽게 하면 저장소를 여는 시간에 SQLite 읽기가 섞여, #26이 만든 콜드 로드 분해(`순수 읽기` / `파싱` / `실효 I/O`)가 더 이상 벡터 파일 하나를 재지 않게 된다. 그 자를 #31이 전후 비교에 쓴다.

**전수 비교를 유지한다.** 근사 최근접으로 바꾸지 않았다. `search_reviews`가 돌려주는 것은 float32 반올림 차이를 빼면 전과 같다.

**mmap을 쓰지 않는다.** `np.load(mmap_mode='r')`로 열면 콜드 로드가 0초로 찍히지만 비용이 첫 검색으로 옮겨 갈 뿐이다. 재는 값을 속이지 않으려고 전부 읽어 상주시킨다.

**치환이다.** JSON 경로를 코드에 남기지 않았다. 형식 플래그도, 예전 파일을 읽는 대체 판독기도 없다. `data/vectors.json`과 `data/scale/*/vectors.json`은 새 코드로 읽히지 않는다(지우지는 않았다).

## 검색 결과가 바뀌지 않는다는 근거

점 1(리뷰 4,744건)에서 **같은 벡터**를 두 형식에 두고 — 옛 JSON 저장소의 벡터를 그대로 float32로 옮겨 — 질의 10개의 상위 10건 `review_id` 목록을 견줬다. 필터 없는 것, 별점 범위, 구매 인증, 상품 한정을 모두 덮었다.

- 코사인 유사도 차이는 **8.8e-08 ~ 1.6e-07**이다.
- 10개 중 9개는 목록이 **완전히 같다.**
- 다른 하나는 정확히 동점인 두 건(같은 본문의 리뷰 두 개, 둘 다 0.5585137)의 **순서만 바뀌었다.** 집합은 같다.

float32는 검색 정확도를 바꾸지 않는다. 바뀌는 것은 동점의 순서뿐이다.

## 고려한 대안

- **근사 최근접(ANN)·벡터 DB 교체 (Chroma, FAISS, LanceDB…)** — ADR-0002가 Chroma를 못 쓴 이유는 개발 PC(Windows 11)에서 나던 access violation이었다. 지금 도는 곳은 Linux이므로 **그 장애물은 사라졌고, 이 후보는 진짜로 쓸 수 있다.** 그래도 고르지 않았다. 첫째, 가장 낮은 벽을 넘기는 최소 변경이 아니다 — 그 벽은 검색 계산이 아니라 적재 파일의 읽기·파싱이고, 저장 형식만 바꾸면 넘는다. 둘째, 근사 검색은 검색 정확도를 바꾸므로 스펙 #23이 recall@k 평가를 같은 티켓에 넣으라고 요구하고, #31의 전후 품질 비교도 흐려진다. 전수 비교를 유지하면 검색 결과가 그대로라 비교가 깨끗하다.
- **SQLite 인덱싱** — 스펙 #23이 "곡선이 `run_sql`의 기울기 증가를 보여줄 때만"이라는 조건을 걸어 두었다. 곡선은 보여주지 않았다. `run_sql`이 일곱 점 전부에서 0.1초 미만이고 가장 큰 점의 SQLite도 152MB다. 조건 미충족.
- **RDBMS 교체**, **기계 증설** — 스펙 #23의 Out of Scope.
- **벡터 파일을 압축하는 것**(gzip 등) — 읽는 바이트는 줄지만 푸는 CPU가 붙고, 상주 RAM과 검색마다의 복사는 그대로다. 네 재료 중 하나만 민다.

## Consequences

- 벡터 파일이 6.7배 작아지고, 리뷰 벡터가 파이썬 객체가 아니라 numpy 배열로 상주한다. 실측값은 아래 "측정" 절에 있다.
- **`search_reviews`의 입출력과 그 테스트는 그대로다.** ADR-0002가 한 약속(ADR-0001의 도구 경계)을 지켰다. 바뀐 것은 `open_store`가 SQLite 경로를 같이 받는 것뿐이다.
- **`langchain_core`의 `VectorStore` 인터페이스에서는 내려왔다.** 그 인터페이스가 요구하는 `Document` + `list[float]` 표현이 바로 이 ADR이 없애는 비용이다. 저장소를 또 바꿀 때 갈아 끼울 자리는 `search_tool.py`의 `ReviewVectorStore`·`open_store`·`search_reviews` 셋이고, 에이전트·하네스·케이스는 여전히 저장소 종류를 모른다.
- 벡터 파일 하나로는 리뷰를 인용할 수 없다. 검색 결과를 만들려면 SQLite가 옆에 있어야 한다. 두 파일은 원래도 같은 적재 실행이 함께 만들고 함께 쓰이므로 새 제약은 아니지만, 벡터 파일만 따로 옮기는 일은 이제 뜻이 없다.
- 적재도 임베딩을 1,000건씩 float32로 바꿔 쌓는다. 한 번에 다 받으면 리뷰 27만 건에서 파이썬 실수만 약 13GB가 동시에 살아 있다.
- **다시 열어야 할 조건**: (ㄱ) 다음 벽이 적재가 아니라 **검색 계산**에 걸리면 — 상품을 한정하지 않은 검색은 여전히 리뷰 수에 비례하는 전수 비교다 — 그때는 ANN을 다시 본다. 그 티켓은 recall@k 평가를 같이 진다. (ㄴ) 상주 RAM이 다시 벽이 되면(리뷰당 6.1KB이므로 RAM 33GB에서 리뷰 약 500만 건) 디스크에 남기는 색인이나 차원 축소를 본다. (ㄷ) 적재 데이터를 여러 프로세스가 함께 써야 하게 되면 프로세스마다 행렬을 한 벌씩 드는 지금 구조가 맞지 않는다.

## 측정

일곱 점을 새 형식으로 다시 적재하고, 곡선이 깨졌던 점 7과 품질 기준선이 있는 점 1에서 전체 평가(케이스 18개 × 3회)를 `/usr/bin/time -v` 아래에서 돌렸다. 곡선 전체의 재측정은 티켓 #31이 한다.

### 점 7 (리뷰 269,114건) — 전에는 SIGKILL로 죽던 점

| | 전 (#29) | 후 |
|---|---|---|
| 콜드 로드 | 202.9s | **12.7s** (16.0배) |
| ㄴ 순수 읽기 / 파싱 | 83.0s / 119.9s | 11.7s / **1.0s** |
| 전체 평가 (18개 × 3회) | **커널 OOM 킬러가 SIGKILL** (6분 37초 지점) | **끝까지 돎** · 4분 15초 · 49/54 |
| 피크 RSS | 31.04GB (OOM) | **1.85GB** |
| 리뷰당 상주 | 104KB + 검색당 36KB | **6.9KB** |
| `search_reviews` 합계 | — (죽어서 못 잼) | 17.0s |

**세션 시작 30초 벽도 점 7에서 넘지 않는다** — 12.7초다. 벽이 리뷰 4.1만 건에서 가장 큰 점 밖으로 밀려났다.

파싱이 119.9초에서 1.0초가 됐다. 콜드 로드의 92%가 이제 순수 I/O이고, 남은 것은 파일 크기와 볼륨 대역폭(142MB/s)뿐이다. 이 벽을 더 밀려면 다음에 줄일 것은 파일 크기다.
